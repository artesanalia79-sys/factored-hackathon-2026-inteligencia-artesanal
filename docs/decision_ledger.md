| 2026-10-02 | auth | T7 OTP limits: 6-digit mock OTP, 5 min TTL, 3 wrong codes close a challenge, and 5 wrong codes per customer in 15 min lock new challenges and verifications until the window passes (a new code does not reset the count; a successful login forgets only its own counted attempt, never earlier wrong guesses). Every verification runs the lockout check, spends one attempt and counts one failure in a single store transaction before the code is compared, so guesses fired in parallel over many challenges cannot exceed either limit. Trade-off accepted: anyone can lock a persona for 15 min with 5 wrong codes; without the lockout a 6-digit code falls to repeated challenges. Client strings that are not plain ASCII are rejected before any hash, comparison or query; 422 responses never echo the rejected input (`SafeValidationRoute`); challenges and failures older than the lockout window are purged on each login start. Only a keyed hash of the code is stored. Unknown persona, wrong, expired and reused codes all return the same `invalid_credentials`. The mock OTP is returned in the login response only when `AUTH_EXPOSE_MOCK_OTP=true` (off by default; `.env.example` opts the local demo in) and the service refuses to start with it unless the data is synthetic, checked against both `DATA_MODE` and the serving DB's own `_serving_metadata` (PR #41 review). `APP_SECRET_KEY` must be >= 32 bytes with >= 12 distinct characters; `poe init-env` is the supported way to create it.
