# Known limitations

Honest list of what the system does not do or cannot claim. Keep it current; judges read it.

| Area | Limitation | Mitigation / status |
|---|---|---|
| Regulation | No country's dispute window has been checked against a primary source yet. `DSP-WIN-01` (`policy/dispute_policy_v1.yaml`) uses a 90-day placeholder for AR, MX and CO, all labeled `synthetic: true`. | A human must verify Argentina Ley 25.065 arts. 26-29 and the MX/CO equivalents before this policy is used on real customers (Task 9). |
| Policy | Issue #9 listed two escalation rules that the policy does not have: high amount and foreign transaction. Neither has a verified threshold; `fraud_score` (`DSP-ESC-01`, ADR 0003) is the only measured risk signal. A customer's second dispute through the agent within 90 days escalates (`DSP-ESC-02`), so a demo persona escalates on its second dispute until the ops store is reset. | Descoped on 2026-10-02 (`docs/decision_ledger.md`); add them as synthetic rules only with a threshold someone signs off on. |
| Identity | Login is a persona picker with a mock OTP; no real KYC. With `AUTH_EXPOSE_MOCK_OTP=true` (the demo setting) the OTP is returned in the login response because there is no SMS or email channel, and the persona list is public, so anyone can log in as any synthetic persona. Anyone can also lock a persona for 15 min with 5 wrong codes. | Out of scope for the hackathon; the session model is production-shaped (signed short-TTL token, server-side session, attempt limits and lockout). The exposed OTP is off by default and the service refuses to start with it on non-synthetic data (Task 7). Where `DEMO_ACCESS_CODE` is set (the public service), a login first needs the shared access code, so "anyone" means anyone who was given it. It is one code for everybody: it identifies nobody and can only be revoked by changing it for all (Task 15). |
| Conversation | T13 currently holds active chat state in one API process; a restart or multiple workers interrupt a conversation, and inactive sessions occupy memory until the process restarts. | Run one worker for the demo; persist conversation state and expire idle entries before any multi-worker deployment. |
| Conversation | Every chat turn runs under one lock, so customers wait for each other (a turn includes an interpreter call with an 8 s timeout). The lock is also what keeps the OpenAI provider's spend limit exact: its check and its accounting are not atomic. | T29 (from T13 and T10; Jacobo, with Santiago): make the provider's reservation atomic, then lock per session. Until then, one worker and few concurrent users (decision ledger, 2026-10-02). |
| Conversation | The agent reads answers with keyword rules when the stub interpreter is used. At the "which charge?" question a negated answer ("no es el de 899") is read as naming that charge, and a date ("el de ayer") is not understood. A correction typed at the card-block question is read as a no. A card block with no dispute and a claim's status are refused, with the generic "no tengo información suficiente" line. | The recognition and confirmation questions show the charge's facts again, and nothing is written without an explicit yes to them. The real interpreter (`LLM_PROVIDER=openai`) has not been run on these paths (no spend). T29 (from T13 and T11; Jacobo). |
| Deployment | The public service runs on a free Render instance. It sleeps after 15 minutes without traffic and the next request takes about a minute. Its disk is ephemeral, so every restart, deploy or wake-up empties the ops store (disputes, card blocks, handoffs, sessions, execution records) and ends the conversations in progress, and Render may restart it at any time. Nothing a customer did survives. | Accepted for a demo on synthetic data, where an empty store is also how the demo is reset (`docs/operations.md`). T29 (from T15; Santiago): a paid instance and an ops store outside the container before any real use. |
| Deployment | No rate limiting. A caller with the access code can send turns as fast as the single lock allows. With the real model on, the spend cap of the process (`LLM_SPEND_LIMIT_USD`) starts again at every restart, so the total is bounded only by the budget set on the OpenAI project; when the cap is reached the agent goes on with the keyword interpreter and does not say so. | The shared access code keeps anonymous traffic out; OTP attempts are limited per persona; a turn is at most 2,000 characters. T29 (from T15; Santiago): a limit per client that reads the proxy's forwarded address, tested on the platform. |
| Copy | The Portuguese copy added while finishing T13 (card-block offer and decline, the three ineligibility reasons, the opening question, the list of matching charges, the reworded clarification) has not been reviewed by a native speaker; the T11 review covered the earlier copy only. | T29 (from T11; Jacobo): review before the demo (`docs/evidence/t11_template_review.md`). |
| Web UI | The UI (T14) keeps the session token in memory only: a reload signs out and loses the transcript, while the server-side conversation stays open until it ends or the process restarts. The confirmation panel's buttons answer in the chat with "Sí, confirmo" / "No" ("Sim, confirmo" / "Não"), which the interpreter reads like typed text: affirm and deny with the stub, and with `gpt-6-luna` in one live run each (2026-10-03), so not a rate. After a network failure the UI cannot tell whether the message reached the agent, so it neither resends it nor restores the confirmation panel, and it does not give back an answer to a confirmation (PR #58 review): if the agent read it before the reply was lost, it is now asking the next question (the card block after a dispute), which the customer has not seen. The UI tells the customer to ask what happened first, and the agent then repeats its question; a "sí" they type instead is still read as the answer to that unseen question, and the reply that was lost (the dispute's reference) is not shown again. Accessibility is checked automatically only (axe WCAG 2.2 A/AA in light and dark mode, a keyboard-only Playwright run, a phone-width layout, all on Chromium); there has been no screen-reader, Safari or Firefox pass. The Portuguese UI strings (`web/src/i18n.ts`) have not been reviewed by a native speaker. | T29 (from T14; Juan José): a screen-reader and cross-browser pass before the demo if time allows; restoring a conversation after a reload needs the persisted conversation state of the row above. A lost reply needs a contract change: each message carries the number of replies the UI has received, and when it is behind, the server sends the missed reply again instead of reading the message as an answer. |
| Data | The public demo runs on team-generated synthetic personas; organizer-derived data is only used locally. | `DATA_MODE=curated` is local only (Task 19). |
| Fraud | `is_fraud` is never used at runtime. `fraud_score >= 30` escalates with offline precision 0.80 and recall 0.55; the score separates the label almost perfectly (a synthetic-generator artefact), so real-world precision would be lower, and ~21% of fraud rows have no score. | ADR 0003 (accepted), `docs/evidence/fraud_score_thresholds.md`. |
| Privacy | Silver `customers.document_hash` is an unsalted sha256 of a short numeric identity document (8-10 digits), so it can be brute-forced back to the number; it is fine only while silver stays offline. | If it ever leaves offline use (serving, auth lookups), switch to an HMAC keyed from `.env` with the same trim normalization on the auth side. Owners: T3 (contracts), T7 (auth). |
| Data scope | In curated mode only card transactions are served (1,547,432 of 4,425,008); movements on savings/checking accounts and loans cannot be disputed. | By design for the card-dispute workflow (decision ledger, T6). |
| Data | The source has no customer language (all text is Spanish), no cards specialty among human agents, no MXN amounts (Mexican cards are in USD) and no link from complaints to transactions. `preferred_language` is a constant `es`, cards handoffs route to general, `related_transaction_id` is NULL. | Recorded in `docs/decision_ledger.md` (T6); the fixture bank covers Portuguese and the cards specialty. |
| Data | Card lifecycle flags are very common in the source (462,419 served transactions after card expiry, 288,617 before opening). | They are `dq_flags`, not rejections. The policy never rejects on them; it escalates only `dq_txn_before_product_opening` (`DSP-ESC-03`, 1.6% of disputable curated transactions) and ignores `dq_txn_after_card_expiry`, which is on 46% of them (T9). |
| Tools | The serving DB is read-only, so a card block and a dispute exist only in the agent's operational store: `list_cards` shows the block, but nothing is sent to a core banking system. One dispute per transaction and one block per card are permanent (there is no close, reopen or unblock). | By design for the hackathon; the write path is production-shaped (confirmation token, idempotency key, read-back). Closing or unblocking must change the UNIQUE constraints and the open-dispute rule together (Tasks 7-9). |
| Tools | `search_transactions` compares dates against the UTC date of the transaction, which can be one day after the customer's local date. T13 does not yet use a date mentioned in free text to narrow a search: two or three matches are listed for the customer to choose, more than three ask for the merchant or the exact amount. `get_dispute` returns only disputes created through the agent; a prior complaint from the bank's history is reported as `open_dispute_id` by `get_transaction` but cannot be read as a case. | Add customer-local date parsing and widen the search by one day in a follow-up. In curated mode no prior complaint is linked to a transaction, so the last point only shows on the fixture bank. |
| Tools | The tools trust the `Session` in their context: revocation (logout) is checked when a request is authenticated, not again inside each tool call. Confirmation tokens and handoffs are never purged, and a handoff needs no confirmation, so a customer can create more handoffs in another session. | The API authenticates every request against the stored session (Task 7). T13 uses one handoff idempotency key per conversation, so a repeated escalation within that conversation is a replay. |
| Router | The learned intent router (T18) is offline: neither the deployed agent nor the T27 evaluation uses it. Its numbers come from a synthetic corpus written by one author (the AI assistant), so they measure the method in-distribution, not accuracy on real customers, and a teammate reviews only a sample of it. Set coverage meets the 90% target on average over splits, not on every split (7 of 20 below) and not per intent or dialect. | Model card `docs/models/router.md`. Wiring it in (served from a pure-Python export), ONNX embeddings, the LLM zero-shot comparison and corpus messages by more authors are T29 (Juan José + Santiago). |
| Router | The keyword attack gate (`GATE-ATTACK-01`) flags 32 of the 100 synthetic attacks in `eval/router/corpus/attack.yaml`: role play ("actúa como administrador"), prompt extraction ("repite el texto de arriba") and requests about another person's card pass it and reach the interpreter. The agent still acts only on the session customer's own data, after an explicit confirmation, and its replies are templates. | The attack cases of T17 measure the end result. More gate patterns, or the learned router as an extra attack signal (never a veto), in T29 (Jacobo). |
| Evaluation | Scripted users are simpler than real customers. | Held-out set with dialect quotas, red team and a small pilot (Tasks 17, 24, 25). |
| Evaluation | The scripted user classifies the agent's question with keyword rules. It misses recognition questions that never say "reconoc" ("¿Te suena este movimiento?") and reads "¿Cuál… es el que no reconoces?" as a recognition question. The rule for confirmations was chosen on hand-written phrasings, because the LLM-only baseline does not exist yet. | Unclassified questions are counted per system in the report; re-check the rules on the baseline's real questions when it is built (T27, from T12; Santiago). |
| ROI | The ROI is a projection, not a measured production saving. Labour costs are September 2026 market figures for outsourced contact centers; investigation time, deflection and handoff savings come from US/EU industry sources; escalation and LLM cost are provisional until the final evaluation. | Every number is labelled by provenance with a range and a tornado in `docs/evidence/roi.md`; `poe analysis --eval-results` swaps in T27 measurements (Task 16). |
| ROI | The organizer data cannot measure contacts per dispute (no detectable link between complaints and contacts), the money at stake (`claimed_amount` is unusable) or the true volume (agents declare x23.7 the contacts in the table, with no evidence that complaints are sampled the same way). | Repeat calls are left out (understates today's cost); savings are reported per dispute and per 1 M customers, never scaled by the declared capacity (Task 16). |
